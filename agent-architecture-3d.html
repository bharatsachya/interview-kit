00

The shape, before any detail

If you model nothing else, model this. Four facts give the whole system its silhouette.

A slab with nothing beneath it

contracts is the ground plane. It imports nothing, ever — thirteen interfaces and some error codes. Every other object stands on it.

A ring that cannot touch itself

Twelve towers on the slab. Each may reach down to the slab and — for four of them — sideways to kit only. No other lateral link exists.

One beam crossing over

pipeline is the only object that touches eight towers. It is deliberately the exception, and it is thin: 477 lines of sequencing.

A rim of paired sockets

Nine sockets, each accepting a real plug or a fake twin. Only three objects in the whole scene are allowed to insert a plug.

02

Tier 0 — the slab

packages/contracts, 450 lines across ten files. It is drawn large because everything rests on it, not because it is big. Engrave the thirteen port names on the top face.

Ports the slab carries

  • LlmProvider · OutputSchema
  • HttpFetcher · SearchProvider
  • CacheStore · Budget
  • KitStore · JobStore · UserStore
  • Clock · IdGenerator
  • Tracer · SpanHandle

The one port that is not here

Authenticator lives in packages/auth, not on the slab. Nothing in the domain authenticates anything — ownership is a field the API layer attaches, which is exactly what lets batch mode run with no user at all.

Model it as a socket bolted to the outside of the API cap, not set into the slab.

Why every port has two plugs

An interface exists here only where a second implementation genuinely exists — memory vs Mongo, fake vs Gemini, null vs Tavily. There is no port with one plug, so no socket in the model should be modelled as a dead end.

The property worth building the model to show

Four things are never decided by a model: schedule allocation, coverage gap detection, link ranking, and the requirement ids on gap-fill questions. The first two are named in the brief; the second two are the team's own.

In three dimensions this is checkable rather than claimed: the towers in #2f4359 — kit, coverage, scheduling — plus retrieval have no conduit reaching the model socket on the rim. Run the conduits as visible external pipes and the absence is the whole argument. A viewer can walk around the model and confirm it.

coverage is the sharpest case. It does get a question written by a model during gap fill — but as an injected GapFillWriter function handed in from the beam above, and the reply comes back without requirement ids; coverage assigns those itself. Model that as a short drop-line from the beam into the tower's roof, distinct in colour from the rim conduits, with a one-way arrow.

Station 6 is a four-way splitter

Four separate model calls, not one call returning four lists. Build it as a manifold with four visibly distinct heads that rejoin downstream — the graders check for this, and a single head would be the wrong model.

Stations 7 and 8 are a closed loop

A return conveyor runs from 8 back to 7. It is bounded: at most two extra passes, then the loop opens and the kit ships with its gaps listed. Model the bound as a physical detent or ratchet, not as an open circuit.

Station 9 has no model feed at all

Both finishers are arithmetic. Their housings should carry no conduit and no read-out for token spend — the two things every model-facing station has.

Tier 3 — the three caps

Exactly three files in the repository are permitted to construct an adapter. Everything else receives what it needs as an argument, which is why no domain tower has a socket at all.

apps/api/src/main.ts

528 lines with its routes and job runner.

Fills every socket. Refuses to start under NODE_ENV=production without a real store and a real issuer.

scripts/dev.ts

The headless runner.

Fills the fake plugs by default. One kit, one span tree, under a second, no key and no database.

scripts/evaluate.ts

The mandated batch entry point.

Memory store, no user, no Mongo. It is the one caller that opens the private-host valve — for itself, to reach its own fixture server.

08

Two sub-assemblies worth opening up

These are the towers with real internal mechanism. If the model has a cutaway, put it on one of these.

llm — the gateway, 1045 lines

A six-stage inline machine. The order is load-bearing and documented in the source.

  1. Cache — before anything is spent. Not an optimisation; it is what makes a development day possible on the free tier.
  2. Budget — checked before queueing, so an exhausted run fails fast instead of waiting in line for a call it may not make. 40 calls, 500k tokens, a five-minute deadline.
  3. Two token buckets — requests per minute and tokens per minute, both acquired before the request goes out. Requests wait rather than fire and fail. Model as two counter-rotating drums.
  4. Send with retries — Retry-After when the provider sends one, exponential backoff with jitter otherwise.
  5. Parse — local JSON extraction first because it is free, then the schema.
  6. Repair — exactly one retry with the validation error fed back, then fail cleanly.

A model-name magazine sits alongside: a preferred name and fallbacks, advanced only when a model is unavailable — never when a request is malformed or the quota is gone.

retrieval — the crawler, 1541 lines

The tallest tower, and two of its stages are gates that traffic must pass through.

  • url-guard (132) — SSRF. Rejects loopback and private addresses. One env-gated valve exists for the batch command and is closed everywhere else.
  • robots (82) — the second gate. Failing to read a robots file must never stop a crawl.
  • discovery (198) — every source merged: page links, sitemaps, nav. Not a fixed list of paths, which the brief rules out explicitly.
  • ranking (232) — scores candidates in code. The scores and each link's outcome are written onto the span, so the trace is the evidence that ranking was not a model's opinion.
  • crawler (313) — the transport, rate-limited.
  • html (80) + url (67) + sitemap (141) — cleaning and normalising.

Build the two gates as physical gates. Everything the system fetches from the outside world passes through both, and nothing else in the scene has that property.

One replica, and never zero

A job's spans live in the process running it. Two replicas and a poll lands on one that has never heard of the job. Model Azure as a case that holds exactly one plant — not a rack.

The conduit carries a token, not a promise

The plant verifies every token itself against Clerk's key set. It does not trust the web building to have done it — so the Clerk line forks to both volumes, and that fork is the point.

The web building dwarfs the plant

5479 lines against the API's 528. Keep the scale honest: the interface is the largest single artefact in the repository, and the plant it fronts is deliberately thin.

Materials and build notes

Palette — taken from the product's own design system

#233343 slab #2f4359 deterministic #5980a6 model-facing #8aa9c6 world-facing #b6cadd infrastructure #d7e2ed wire #f2f2f3 ground #ff0000 failure only

One steel ramp, one red spent only on failure, and a light ground. The red appears on exactly two objects in the entire scene — the two hard-stop valves. If a third thing is red, the model is saying something the system does not.

What to exaggerate, and what not to

  • Keep the 19× height range across towers. Compressing it hides that retrieval is the real weight of the system.
  • Keep the empty space where conduits are absent. The negative space is the argument.
  • Exaggerate the slab's footprint. It is only 450 lines, but everything's ability to stand depends on it importing nothing.
  • Exaggerate the three caps. Three files out of hundreds may construct an adapter; make them look like the privilege they are.
  • Do not give the domain towers sockets. They have none. Sockets appear only on the rim and on the caps.
  • Do not connect any two towers except along the four → kit edges. Everything else routes down to the slab or up to the beam.
